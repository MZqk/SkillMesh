# SkillsMap 项目入口

本项目已经完成“市场与生态调研 → 本机 Skill 清单 → 共享工作流持久化 → stdio MCP → Project Brief → 九阶段开发手册 → 模板迁移/网页人工确认 → 执行与分级验证记录 → Skill 受控安装 → 重新扫描与复评”的闭环。

- 可运行工具：[Capability Atlas 0.6](./prototype/README.md)
- macOS 双击启动：[启动能力测绘台.command](./prototype/启动能力测绘台.command)
- 功能与安全验收：[0.6 验收记录](./prototype/VALIDATION.md)
- 市场、竞品与 Agent 生态调研：[完整调研报告](./agent-skill-workflow-map-research/report.md)

工具默认只监听 `127.0.0.1`，通过本机 stdio MCP 接受 Agent 草案并统一保存历史。可信 MCP 连接会自动探测并托管独立的 Web 后台；`open_web_ui` 只在用户明确要求时打开浏览器。MCP 可协助建立 Brief、工作流、手册草案和安装提案，但不能冻结/确认手册、记录人工执行进度或执行安装；这些动作只在网页完成，系统不会自动运行 Skill 或项目命令。

## 当前项目的实际使用流程

### 1. 首次启动与连接

1. 进入 `prototype`，运行 `npm install` 和 `npm start`；需要 PDF 时再运行 `npm run setup:pdf`。
2. 打开 <http://127.0.0.1:4317>，或在 macOS 双击 [`启动能力测绘台.command`](./prototype/启动能力测绘台.command)。
3. 将 [`mcp-server.mjs`](./prototype/mcp-server.mjs) 配置到 Codex、Claude Code 或 Gemini CLI。MCP 与网页必须使用同一数据目录，才能看到相同的工作流、Brief、手册和确认历史。

完整命令和 Host 配置见 [`prototype/README.md`](./prototype/README.md#启动网页)。

### 2. 由 Agent 建立工作流草案

网页不通过一段自然语言直接创建工作流。用户先在 Agent 对话中描述项目目标，由 Agent 通过 MCP：

1. 调用 `create_requirement_workflow_draft` 保存结构化需求，并选择 Web、Android 或通用参考流程。
2. 调用 `atlas_status`、`search_skills` 和 `assess_workflow`，把每项能力与本机可用 Skill 对应起来。
3. 调用 `create_project_brief_draft` / `update_project_brief_draft` 建立 Project Brief 草案。

草案写入共享工作区后，网页会自动发现；用户在左侧“当前工作流”中选择它。

### 3. 在网页确认能力与 Skill 映射

用户逐阶段查看必需能力和本机候选，并对候选执行“确认、部分、排除或待确认”。这里确认的是“这个 Skill 是否适合覆盖该能力”，不是证明 Skill 已经运行成功。

只有人工确认的本地匹配会成为手册中的可靠主选；证据不足的候选仍会标成“待确认”，缺失能力则保留人工回退和可选的外部 Skill 搜索路径。

### 4. 补齐并冻结 Project Brief

进入网页“开发手册”，补齐项目名、问题、目标用户、首要结果、首版范围、非目标、约束、成功标准、平台和技术栈。页面会持续显示下一项缺失问题。

用户核对后冻结 Brief。冻结版本是手册生成的不可变输入；后续修改会创建新草案，不会改写旧手册引用的 Brief。

### 5. 生成并审阅开发手册

Agent 或网页显式生成 Playbook。Web 项目使用固定的九阶段、18 步模板。生成结果不再以宽泛开发理念为主体，而是为每个阶段和步骤明确：

- 本阶段的 Skill 执行地图；
- 每一步的主 Skill、备用 Skill、确认状态与负责范围；
- 主 Skill 必须持续使用到什么程度，备用 Skill 何时才可替代；
- 必须交付的产物、验收标准和必须保存的证据；
- 满足哪些条件后才能进入下一阶段；
- Skill 不可用或匹配不足时的人工回退方式。

通用操作建议、调用提示词和失败恢复仍然保留，但收在步骤的折叠参考区，不代替 Skill 完成尺度和阶段门。

### 6. 确认手册版本

用户先在网页审阅当前草案相对基线的结构化差异和内容哈希，再点击“人工确认当前手册”。确认后生成不可变版本，才能开始记录执行进度。

如果九阶段模板的版本或内容指纹发生变化，必须按“预览模板迁移 → 应用为新草案 → 重新审阅 → 人工确认”处理。系统不会静默覆盖旧版本、旧进度或旧验证证据。

### 7. 按阶段执行手册

每个步骤按以下顺序执行：

1. 先查看“本阶段 Skill 执行地图”，确定本步骤主 Skill 与备用 Skill。
2. 使用主 Skill 完成其“负责范围”；只有主 Skill 不适用或证据不足时，才使用备用 Skill。
3. 持续执行到“做到什么程度才算完成”的全部条件满足。
4. 保存手册要求的产物和证据，在网页把步骤标成“已完成”并将验收结果设为“通过”。
5. 本阶段所有步骤都完成且验收通过后，填写质量门判断依据并通过阶段门；硬门还要求每个步骤已经保存证据。
6. 下一阶段只有在依赖阶段的质量门已“通过”或被确认“不适用”后才能开始。

不适用阶段不能直接删除，必须保留最低判断并记录原因。重新生成手册后，旧内容哈希下的进度仍保留，但不会自动套到新版本。

### 8. 验证、导出与迭代

1. 所有适用步骤和质量门完成后，可在网页追加“样例已跑通”的环境、结果和证据。
2. 再由初级测试者按手册独立执行，记录协助程度与证据，升级为“初级开发者已验证”。
3. 从网页导出 Markdown 或 PDF。两种格式都来自同一个已确认 Playbook，并携带冻结 Brief、来源、内容哈希和验证状态。
4. 项目目标、Brief、模板或 Skill 映射发生实质变化时，创建新草案并重新走审阅、确认与验证流程。

### 9. 可选：补齐缺失 Skill

只对明确缺失的必需能力搜索外部 Skill。用户可从能力缺口直接进入网页“生态候选”目录，按功能、来源和组合关系筛选 Skills Atlas 的公开元数据；同一功能组存在多个仓库时，可横向核对许可证、更新时间、热度、安装映射与可绑定 Skill。组合链详情会按目录声明顺序逐项核对本机精确名称覆盖、当前缺口已记录项和待补项，并可把待补成员作为一次原子元数据变更批量记录；链名、组名与成员位置会随候选保存，但目录顺序不等于项目依赖或运行验证。记录候选前可显式读取目录映射的单份 `SKILL.md`，核对仓库、分支、路径、SHA-256、frontmatter、工具声明、带行号原文和静态风险线索；未命中规则不等于安全，对比也不生成综合安全分。Agent 仍可记录候选并提出安装计划，但原文审阅、候选记录、接受候选和安装执行是独立动作；系统不会自动安装或执行。安装完成后系统重新扫描并复评；安装成功不等于运行验证成功。

安装选择保存后，可下载 `capability-atlas.skill-kit.json` 作为项目可提交的 Skill 意图清单。Kit 用稳定 SHA-256 绑定工作流、目标 Agent、能力覆盖和所选本地/外部 Skill，但不携带绝对路径、安装命令或确认人信息。导入 Kit 只会核对“内容一致、本地有改动、已禁用、已有候选、缺失”等状态；不会创建候选或安装计划，也不会安装、移除或清理未声明的本机 Skill。

## Agent 与网页的职责边界

| 环节 | Agent / MCP | 网页用户 |
|---|---|---|
| 工作流与 Brief | 创建、补充草案 | 审阅工作流、冻结 Brief |
| Skill 映射 | 扫描、检索、评估、提出候选 | 确认、部分确认或排除候选 |
| 开发手册 | 生成草案、读取差异、导出 Markdown | 审阅差异、迁移模板、确认不可变版本 |
| 执行与质量门 | 只读进度和验证状态 | 执行 Skill、记录步骤、证据和质量门 |
| Skill 安装 | 搜索候选、提出安装计划 | 审核风险并显式执行安装 |
| 项目 Skill Kit | 无自动同步或执行权限 | 导出意图清单、导入并只读核对本机状态 |

核心原则：Agent 负责提案和编排，网页负责会改变可信状态的人工确认；Capability Atlas 本身不自动运行 Skill、开发命令或测试命令。
